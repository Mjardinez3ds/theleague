## What this project is

A read-only website that surfaces all-time data for **The League** (ESPN
league id `1917791320`), targeting an audience of ~12 managers who view
exclusively from their phones. Designed to **install as a PWA** ("Add to
Home Screen" → fullscreen, app-icon launcher, dark theme).

Sister project: [`sportsbook-bot`](../sportsbook-bot) — Telegram bot that
shares the same league surface area; both reach ESPN through a similar
`fantasy_espn` module and both implement the **owner identity resolution**
algorithm described below. Keep the two implementations in sync.

## Stack

- **Next.js 16 (App Router)** — fully prerendered with `force-static`.
- **Static export** — `next.config.ts` sets `output: "export"`, so production builds emit an `out/` directory.
- **TypeScript** — strict.
- **Tailwind CSS v4** — design tokens declared in `globals.css` via `@theme inline`.
- **lucide-react** — icon set used by the bottom tab bar.
- **Python 3.12 + `espn-api`** — data pipeline only (`scripts/build_data.py`).
- **GitHub Actions** — hourly cron to regenerate JSON + commit it back.
- **Cloudflare Pages** (planned) — hosting target. Free tier, fast CDN.

No database, no API server, no auth — the entire site is a static export
hydrated from JSON files in `/public/data`.

## Architecture

```
ESPN unofficial Fantasy API
         │  (espn-api Python lib)
         ▼
scripts/build_data.py
         │  writes JSON
         ▼
public/data/*.json     ←  also committed to git so the site can be rebuilt
         │              from a clean checkout without ESPN access.
         ▼
src/lib/data.ts (typed loaders)
         │
         ▼
src/app/**/page.tsx   ←  Server Components, force-static.
         │
         ▼
Static HTML + PWA manifest
         │
         ▼
Cloudflare Pages CDN
```

**Data is regenerated by a separate Python process, never by the site at
runtime.** This keeps the site hostable on any static CDN and lets the data
refresh independently of code deploys.

## Owner identity resolution (read this before touching `build_data.py`)

ESPN's per-team owner records are inconsistent across seasons:

- **Same person, different ESPN UUIDs** — managers who delete/recreate their
  ESPN account get a brand-new owner id. Example: Ricky Cano played 2023
  under one UUID and 2025 under a different one.
- **Different people, same first name** — "Kevin Liang" and "Kevin Llerena"
  collide under a naive `firstName + last[0]` formula. The old abbreviated
  "Kevin L." / "Kevin Ll." approach was replaced with full names (see below).

`scripts/build_data.py::build_owner_resolution()` solves both:

1. **Auto-merge** — group raw ESPN owner ids by lowercased
   `(firstName, lastName)`. All ids in a group collapse to one canonical id.
2. **Full-name display labels** — each canonical owner now gets
   `"First Last"` as their display name and `first-last` as their URL slug.
   If two owners somehow share an identical full name, a `#2` suffix is
   appended (has never happened in this league).
3. **Slug collision guard** — if two slugs still collide for some reason,
   the later one gets `-2` appended.

**Current slug list** (as of 2026-05-11):
`chris-peralta`, `marcus-jardinez`, `george-duran`, `junior-peralta`,
`derf-punk`, `kevin-liang`, `kevin-llerena`, `devon-malki`,
`abraham-pinales`, `anthony-richardson`, `ricky-cano`, `super-shyguy`,
`matthew-taylor`, `faust-vinas`, `christopher-jones`, `denniell-grijalva`

**Important:** switching from abbreviated to full names changed every slug
(e.g. `kevin-l` → `kevin-liang`). All JSON files were regenerated and old
abbreviated files deleted. If you ever need to re-run `build_data.py`,
ensure old slug files are purged — the script adds new ones but does not
remove the stale ones.

**Trade-off**: two unrelated humans with identical first+last names would
get falsely merged. Acceptable risk in a 12-person league. If it ever
happens, add an explicit override in this file and split them by raw id.

The bot project mirrors this in `fantasy_espn.py::resolve_owner_display`.
**Keep both implementations in sync if you change the algorithm.**

## Mobile-first design rules

When adding new pages:

- Use `force-static` page export so everything pre-renders.
- Pad page top with `pt-6` and bottom with `pb-4` (the layout already
  reserves space for the bottom tab bar via the body's `pb-[calc(64px+...)]`).
- Cards: `rounded-2xl border border-app bg-elev p-3-to-4`.
- Lists are vertical, full-width, big tap targets (≥44px high). Use
  `active:bg-elev-2` for tap feedback (no hover states — touch-only).
- Numbers: `tabular-nums` so digits don't shift around.
- Don't introduce horizontal scrolling. Truncate long names with `truncate`.
- Section labels: `text-[11px] font-bold tracking-widest text-accent`.
- Manager links go to `/managers/[slug]` — never link by team name.
- Avoid emoji-only signal in critical UI; pair with text/colour for accessibility.

## ESPN API gotchas (hard-won, save the next agent some hours)

The `espn-api` Python library and ESPN's underlying Fantasy API have several
quirks that are not documented anywhere. Add to this section every time you
hit a new one.

### Two different API hosts
ESPN serves the Fantasy API from two different hosts and they behave
differently:

| Host | What it serves | Notes |
|---|---|---|
| `lm-api-reads.fantasy.espn.com` | Standings, rosters, settings, transactions, draft, players | **The reliable one.** No WAF, accepts Python `requests` with default User-Agent. This is what `espn-api` uses for almost everything. |
| `fantasy.espn.com` | The `/communication/` (activity feed) endpoint, only | Has a Cloudfront WAF that blocks Python's default UA with 403. With a browser UA it returns 202 + empty body — *regardless of authentication* — so it appears unusable from Python. |

### `recent_activity` / `recent_activity(msg_type='TRADED')` is broken from Python
The library calls `lm-api-reads.fantasy.espn.com/.../communication/` which
returns 404 (endpoint doesn't exist there), and the library raises
`ESPNInvalidLeague: League X does not exist` — a misleading error. Switching
to `fantasy.espn.com/.../communication/` returns 202 empty (see above).

**Workaround: use the `mTransactions2` view for trades** (see `build_trades`
in `scripts/build_data.py`). The trade reconstruction strategy is documented
in the Trades section below.

### The 401 → 404 fallback in `espn-api`
`espn_api.requests.espn_requests.checkRequestStatus` automatically tries an
"alternate endpoint" (`/leagueHistory/...?seasonId=X` ↔ `/seasons/X/...`)
when it gets a 401. This is why historical-season standings still work after
ESPN cookies expire. **But:** for endpoints that genuinely don't exist on
the alternate URL (like `/communication/`), this fallback doesn't help and
you get the misleading `ESPNInvalidLeague` exception.

### `lg.player_map` returns `{int: str}`, not `{int: Player}`
Despite the variable name, `League.player_map` is a flat dict of
`{playerId: playerName}` where the value is just a plain string. Don't try
`getattr(p, 'name')` on the value — `p` is already the name. Used in
`build_trades` for resolving `playerId` → display name.

### Owner UUIDs change between seasons
ESPN gives each `team.owners[0].id` a UUID. The same human can have a
*different* UUID across seasons if they delete/recreate their ESPN account.
We solve this by collapsing on `(firstName, lastName)` — see "Owner identity
resolution" above.

### ESPN cookies (`ESPN_S2`, `SWID`) expire annually
Symptoms: 401s on private-league endpoints (rosters, transactions) but
public ones (settings, basic standings) keep working. Refresh by:
1. Log into ESPN Fantasy in Chrome.
2. DevTools → Application → Cookies → `fantasy.espn.com`.
3. Copy `espn_s2` (URL-encoded) and `SWID` (with curly braces).
4. Update `scripts/build_data.py` defaults *and* the GitHub Action secrets.

### Trade reconstruction strategy (the long, sad story)

**TL;DR — diff weekly mRoster snapshots, then attach dates from
TRADE_ACCEPT timestamps.** All other approaches return fake or rejected
trade data. See `build_trades` in `scripts/build_data.py` for the
implementation.

#### What doesn't work (and why we know)

1. **`/communication/` endpoint** — broken from Python (see "two API hosts"
   section above).
2. **Matching CANCELED TRADE_PROPOSALs to TRADE_ACCEPTs by team-pair +
   timing** — *initial heuristic, since reverted*. The CANCELED proposals
   we can see are all `executionType: "CANCEL"` (genuine rejections /
   withdrawals). The proposals that *got accepted* are stored elsewhere
   (probably in /communication/) and never appear in `mTransactions2`.
   Matching accepts to the most-recent canceled proposal between the same
   teams was just guessing — debug analysis showed median time gaps of
   1–24 hours and many >1 day, meaning most matches surfaced *rejected*
   trades to the user. Don't reintroduce this approach.
3. **`relatedTransactionId` on TRADE_ACCEPT** — points to a transaction ID
   that is not present in any week's `mTransactions2` response, and direct
   `/transactions/{id}` lookups 404. The accepted-proposal data really
   isn't reachable through this view.
4. **`acquisitionType` / `acquisitionDate` on roster entries** — both
   return `None` for every player. ESPN doesn't populate these anymore (or
   we're missing a view to enable them).

#### What works

`mRoster` returned with `scoringPeriodId=N` gives a snapshot of every
team's roster as it was at week N. By diffing consecutive weeks we can
detect any player whose `teamId` changed. A *trade* is identified by a
team-pair (A, B) where at least one player moved A→B AND at least one
moved B→A in the same week-transition — a one-directional move is just
a waiver/drop/add and is filtered out.

Then we fetch `TRADE_ACCEPT` records (EXECUTED) from `mTransactions2` to
attach a real `proposedDate` to each detected trade — match by accepting
team-id + week-of-detection.

#### Known limitations of the diff approach

- **Multiple trades in the same week between the same team pair get merged
  into one entry**: if Team A and Team B trade twice in week 5, the diff
  shows a single combined movement of all 4+ players. The detected count
  is therefore a *lower bound* on actual trades (2025: 16 detected vs 20
  TRADE_ACCEPTs in the API).
- **Trades involving a player who is then immediately dropped won't
  appear** — they leave no roster footprint by the next snapshot. Rare in
  practice.
- **3-way trades** (very rare in this league) would not match the strict
  2-team-pair filter. Build a separate path if it ever comes up.
- The 9-of-2025 / 15-of-2024 / 9-of-2023 unaccounted accepts are a mix of
  the above; the data we *do* surface is correct, just slightly fewer
  rows than the raw accept count would suggest. Better to under-report
  truthfully than over-report with fake players.

### 2026-05-08 (later) — Trade detection switched to roster-diff

**Why:** Owner reported the trades page was showing trade *proposals*, not
actually-accepted trades. Investigation confirmed: my original heuristic
(matching EXECUTED TRADE_ACCEPTs to the most-recent CANCELED
TRADE_PROPOSAL between the same team pair) was just guessing — the
matched proposals had median time gaps of 1–24h from the accept and many
>1 day, meaning the player content shown was from rejected proposals
between those teams, not the actual accepted swap.

**Fix:** Replaced the proposal-matching heuristic in `build_trades` with
a roster-diff approach. Fetch `mRoster` per scoringPeriodId for weeks
1–18, diff consecutive weeks to find players whose teamId changed, and
flag any team-pair with bidirectional movement as a trade. Cross-reference
with EXECUTED TRADE_ACCEPT records to attach the real date.

**Files changed:**
- `scripts/build_data.py` — full rewrite of `build_trades()`. Removed
  `_proposal_involves_two_teams()` helper (no longer needed). New
  approach is documented inline + in the "Trade reconstruction strategy"
  section in this file.
- `AGENTS.md` — replaced the "what works" section with the roster-diff
  strategy + known limitations. Marked the proposal-matching approach as
  a tried-and-rejected dead end so future agents don't reintroduce it.
- `public/data/trades/{2023,2024,2025}.json` — regenerated. Counts now
  35 / 23 / 16 (vs the prior 44 / 38 / 20). The shortfall is expected and
  documented in AGENTS.md (same-week-same-pair trades merge into one
  entry; this is acceptable because the data shown is *correct*).
